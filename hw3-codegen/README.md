# HW3: Code Generator

This stage compiles the C subset to RISC-V assembly. The grammar is the same as in HW2, but the parser actions now build an AST. A second pass walks the AST and writes `codegen.S`. The output is linked with the TA's `main.c` and run on the Spike simulator. Each test checks the `digitalWrite` and `delay` calls that the program makes.

```sh
make codegen
./codegen < testcases/Basic/0.c          # writes codegen.S (RV64)
./codegen --rv32 < input.c               # RV32 output (HW3 Bonus)
riscv64-unknown-elf-gcc spike-sample/main.c codegen.S && spike pk a.out

make test        # RV64: run all tests on Spike (inside the Docker container)
make test-bonus  # HW3 Bonus: RV32 + P-extension, emulated
make test-all    # RV64, RV32 and Bonus
```

Spike prints lines such as `Arduino digitalWrite(26, 1);` and `Arduino delay(1000);`. The test script compares these lines with the expected output.

## Design

`parser.y` contains all of the C code because the submission may only contain three files. The file has five sections: the AST, the grammar, the symbol table, the code generator, and `main`.

- **AST first, code second.** When the whole function is known before any code is emitted, the prologue can allocate the full frame at once. Labels for loops, `break`, `continue` and `return` are also easier to manage.
- **Stack-machine expressions.** Every expression leaves its result in `t0`. A binary operator pushes its left value, evaluates the right side, and then pops the left value into `t1`. Each push uses 16 bytes, so `sp` always stays 16-byte aligned.
- **Stack frame.** `s0` is the frame pointer. `ra` is stored at `s0-8` and the old `s0` at `s0-16`. Parameters and locals follow. Parameters are copied out of `a0`–`a7` into their own slots, so `&param` works.
- **Symbol table.** An array-based scope stack. Lookup searches from the innermost scope outward, so inner declarations shadow outer ones.
- **Types.** `int` and pointers each take one word (8 bytes on RV64). Pointer arithmetic and array indexing scale by the word size.
- **Control flow.** `&&` and `||` short-circuit. `switch` supports fall-through and `default`. Conditional branches use `bnez` followed by `j`, so a jump target can be more than ±4 KB away.

### Limitations

- Only integers and single-level pointers. Float and string literals cause an error.
- Arrays are 1-D only, and the length must be an integer constant.
- A function can have at most 8 parameters. Parameters passed on the stack are not supported.
- On RV64, `int` uses 8 bytes, so overflow does not behave like a 32-bit C `int`.

## HW3 Bonus: Andes P-extension intrinsics

The bonus uses the same `scanner.l` and `parser.y`. The `--rv32` flag, or the environment variable `CODEGEN_TARGET=rv32`, switches the output to RV32 for the Andes Corvette-F1 board. The board supports the P-extension SIMD instructions.


| Intrinsic             | Instruction | Meaning (for each of the 4 bytes)             |
| ----------------------- | ------------- | ----------------------------------------------- |
| `__rv__ukadd8(a, b)`  | `ukadd8`    | unsigned saturating add: `min(a + b, 255)`    |
| `__rv__uksub8(a, b)`  | `uksub8`    | unsigned saturating subtract: `max(a - b, 0)` |
| `__rv__cmpeq8(a, b)`  | `cmpeq8`    | `0xFF` if `a == b`, else `0x00`               |
| `__rv__ucmplt8(a, b)` | `ucmplt8`   | `0xFF` if `a < b` (unsigned), else `0x00`     |

The code generator emits each intrinsic as one instruction, not as a function call. It also adds the `uint32_t` type. When an operand is unsigned, it uses unsigned instructions: `sltu` for comparisons, `divu`/`remu` for division and modulo, and `srl` for right shifts.

### Testing without the board

Standard Spike does not support the P-extension, and I do not have the board. So [bonus/tests/run.sh](bonus/tests/run.sh) checks each of the 5 tests in [bonus/testcases/](bonus/testcases/) in three ways:

1. **Expected result:** compile the test with host `gcc`, with the intrinsics taken from a C reference implementation ([pext_ref.h](bonus/tests/pext_ref.h)). Run it on 12 inputs, including the spec examples and per-lane saturation and equality edge cases.
2. **Emulated run:** build with `codegen --rv32 --pext-emulate`. Each P-extension instruction becomes a call to the C reference, with the same operands. Run the program on RV32 Spike and compare the output with step 1.
3. **Real output:** build with `codegen --rv32`, which produces the `codegen.S` for the board. Replace the P-extension instructions with `nop`, assemble the file with GNU `as` to confirm that the rest is valid RV32, and check that the number of intrinsics matches step 2.

I checked these tests with mutation testing. Swapping the operands of an intrinsic, or using `slt`, `div` or `sra` in place of the unsigned versions, makes them fail.
